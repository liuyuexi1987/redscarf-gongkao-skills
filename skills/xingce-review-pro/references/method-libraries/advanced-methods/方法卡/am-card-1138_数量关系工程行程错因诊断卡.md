# 方法卡：数量关系工程行程错因诊断卡

## 基本信息

| 字段 | 值 |
|------|-----|
| 方法名 | 数量关系工程行程错因诊断卡 |
| 适用题型 | 工程问题、效率、合作工程、轮流工作、行程、相遇追及、平均速度 |
| 触发场景 | 用户做错该类题后，讲解/复盘结束，需要判断错因并写入错因卡或弱点档案时 |
| 步骤逻辑 | ① 先查工作总量/路程是否统一赋值；② 再查效率/速度关系是否正确建立；③ 再查时间分段、相对运动、工程量扣除是否完整；④ 最后归因写入弱点档案 |
| 高频错因 | 总量未赋值、效率比方向搞反、故障/休息时间未扣除、相遇路程倍数误判、平均速度公式用反、相对速度方向错 |
| confidence | high |
| 不适用条件 | 1. 资料分析模块中的工程类计算（如工作量增长率）不在本卡诊断范围
| 反向触发 | 1. 用户做对工程行程题后自行复核答案且无需诊断错因

3. 用户已自行复核正确答案且无错因可诊断时不停留 |

## 诊断流程

### 第一步：查总量与赋值

- 工程题：是否设了工作总量（最小公倍数或公倍数）？是否把总量设成了 1 导致效率出现分数？
- 行程题：总路程是否明确？往返题是否意识到去回是同一段路？
- 用户是否跳过赋值直接列方程，导致效率或速度出现非整数，计算链变长出错？

### 第二步：查效率/速度关系

- 效率比是否直接当效率用？方向有没有搞反（甲效率比乙高 20%→甲=1.2 乙=1 还是甲=1 乙=0.8）？
- 合作工程：效率相加是否正确？轮流工作：是否按周期拆分而非简单相加？
- 行程题：相遇时速度相加、追及时速度相减，方向有没有搞反？
- 平均速度：等距离往返是否用了调和平均数公式，有没有误用算术平均数？

### 第三步：查时间分段与相对运动

- 工程题中间有故障/休息时，是否从总时间中扣除？是否把"共需多少天"和"还需多少天"搞混？
- 行程题第二次相遇：是否意识到总路程变成 3L（从两端出发）？
- 追及问题：是否把追及距离和速度差对应正确？
- 牛吃草/水池进出水：是否把草的生长/进水当作负效率？

### 第四步：查验证与归因

- 结果是否回代验证？工程题算出的天数代回去是否工作量一致？
- 行程题算出的速度代回去是否两次相遇位置对得上？
- 归因到具体步骤：是总量赋值、效率关系、时间分段还是公式选择？

## 错因分类表

| 错因类型 | 判定信号 | 典型表现 | 写入弱点档案的建议标签 |
|----------|----------|----------|------------------------|
| 总量赋值缺失 | 未设工作总量或路程总量，直接用未知数列方程 | 效率出现分数计算链过长，或路程设为 x 导致方程复杂 | 数量-工程行程-总量赋值缺失 |
| 效率比方向搞反 | 甲比乙效率高 20%，设反了甲乙的效率值 | 甲=1 乙=1.2（应为甲=1.2 乙=1），导致结果刚好反过来 | 数量-工程行程-效率比方向错误 |
| 故障时间未扣除 | 中间有停工/故障，但计算时未从总时间中减去 | 算出的完成时间偏大，或工作量重复计算 | 数量-工程行程-间断时间未扣除 |
| 合作效率错加 | 轮流工作时把各人效率简单相加，而非按周期计算 | 轮流做与合作做结果一样，显然不对 | 数量-工程行程-合作效率计算错误 |
| 相遇路程倍数误判 | 第二次相遇时总路程用了 2L 而非 3L | 从两端出发第二次相遇应为 3L，从同端出发应为 2L，搞混 | 数量-行程问题-相遇路程倍数错误 |
| 平均速度公式用反 | 等距离平均速度误用算术平均数 | (V₁+V₂)/2 替代 2V₁V₂/(V₁+V₂)，结果偏大 | 数量-行程问题-平均速度公式错误 |
| 相对速度方向错 | 追及时用了速度相加，相遇时用了速度相减 | 追及问题结果偏小，相遇问题结果偏大 | 数量-行程问题-相对速度方向错误 |
| 牛吃草负效率遗漏 | 忘记草的生长/枯萎是持续的负效率 | 只算了牛吃的速度，忽略了草自身变化 | 数量-工程行程-负效率遗漏 |

## 写回建议

- `数量-工程行程-总量赋值缺失`：工程题未设工作总量，导致效率出现分数，计算链过长中途出错
- `数量-工程行程-效率比方向错误`：甲比乙效率高 20%，设反了导致最终结果互换
- `数量-行程问题-相遇路程倍数错误`：从两端出发第二次相遇，总路程应为 3L，误用 2L
- `数量-行程问题-平均速度公式错误`：等距离往返应用调和平均数，误用了算术平均数

## 使用边界

1. 本卡只用于错因诊断，不替代具体解题方法卡（如 am-card-0711 工程问题三种已知条件解法、am-card-0933 等距离平均速度）。
2. 题干条件不完整（如缺少效率比或路程数据）时，先标记待核验，不硬写错因。
3. 用户给出思路时优先对照用户思路归因；没给思路时只能做低置信诊断。
4. 客观题官方答案冲突时先走冲突复核流程，不立即写错因卡。
